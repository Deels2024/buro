# Production runbook

## Первый запуск

1. Создайте отдельные базы/пользователей PostgreSQL и Redis.
2. Создайте приватный S3 bucket в российском регионе.
3. Заполните секреты из `.env.example`; `BN_PUBLIC_API_URL` в production обязан быть HTTPS.
4. Выполните `alembic upgrade head` ровно одним migration job до запуска новых реплик API.
5. Запустите API и worker, затем проверьте `/v1/health/live` и `/v1/health/ready`.
6. Выполните `python scripts/seed.py` один раз.
7. Войдите номером `BN_BOOTSTRAP_ADMIN_PHONE`, настройте TOTP и удалите bootstrap-номер из обычных инструкций команды.

## Обязательные внешние компоненты

- TLS 1.2+ на балансировщике;
- PostgreSQL 16 с `pgvector` и ежедневными PITR-бэкапами;
- Redis с AOF и отдельными лимитами памяти;
- S3 lifecycle и запрет публичного доступа;
- Secret Manager/Lockbox вместо `.env` в образе;
- централизованные логи по `X-Request-ID`;
- метрики 5xx, latency, Redis queue, webhook failures, OTP rate limits;
- alerting на `/health/ready`, отставание worker и ошибки миграций.

## Резервное восстановление

Раз в квартал проверяйте восстановление PostgreSQL в отдельный контур. Медиа в S3 должны иметь versioning или репликацию. Целевые показатели для пилота: RPO до 24 часов, RTO до 4 часов; перед федеральным масштабированием — RPO до 15 минут, RTO до 1 часа.

## Релиз

1. Сделайте бэкап.
2. Запустите миграции.
3. Разверните одну canary-реплику API.
4. Проверьте OpenAPI, авторизацию, создание публикации, совпадение, заявление, чат и QR-выдачу.
5. Расширьте rollout и только потом обновляйте минимальные версии клиента в system settings.

Архив является готовым интеграционным каркасом, но перед обработкой реальных документов и персональных данных нужны внешний security-аудит, нагрузочные испытания и юридическая проверка модели обработки данных.
