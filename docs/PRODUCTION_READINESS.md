# Приёмка production-релиза

Основной сайт — https://edinburo.ru, кабинет — /app/, администраторы — https://admin.edinburo.ru.

## Проверенный статус на 5 сентября 2026

Релиз `49015ffcb5e8fdbf599c7be5096840669c16dfc0` действительно запущен: публичный API и `/app/release-sha.txt` возвращают этот SHA; база, Redis и worker отвечают `ok`, SMS/OpenAI настроены, транспорт хранилища — HTTPS. Это проверка доступности и конфигурации, а не контрольная платная отправка SMS или запрос OpenAI.

Проверка Deploy №33946415913 завершилась ошибкой после успешного обновления контейнеров: `admin.edinburo.ru` не разрешается в DNS. Для текущего сервера требуется запись `A` для имени `admin` со значением `5.183.191.139`, затем действующий TLS-сертификат и HTTPS-прокси этого имени на существующий шлюз проекта (порт 8088), с сохранением Host. Доступ к панели DNS и конфигурации внешнего TLS-прокси в рабочем окружении не предоставлен; эти настройки не считаются выполненными.

Проверка без секретов и без изменения данных:

```sh
python3 scripts/check-public.py --expected-release "$(git rev-parse HEAD)"
```

`--preflight` фиксирует состояние публичного сайта и админки перед заменой контейнеров. Уже существующий сбой не блокирует доставку проверенных исправлений; финальная приёмка остаётся обязательной. Полная проверка отдельно диагностирует HTTP/DNS/TLS, JSON API, точный SHA API/Flutter, worker, SMS-конфигурацию, HTTPS хранилища и канонические robots/sitemap. Она не считает отсутствие админки успехом. Workflow `Production health` запускает эту проверку каждые 15 минут и сохраняет отчёт в Actions. Доставка уведомлений зависит от настроек GitHub пользователя; отдельные получатели и внешние каналы оповещения не добавляются. Расписание GitHub Actions не гарантирует точную минуту запуска.

## Дополнительная защита эксплуатации

- Общие лимиты SMSC на все номера/IP и реплики: `BN_SMS_HOURLY_LIMIT=200`, `BN_SMS_DAILY_LIMIT=1000`. Значения можно изменить в `.env`; отсчёт ведётся по часам/суткам UTC. Это лимиты попыток отправки, не рублёвого расхода: таймаут провайдера тоже расходует лимит. Превышение возвращает 503 и `Retry-After`, сохраняя уже выданные коды. Это дополнение к лимитам телефона/IP, а не замена CAPTCHA перед масштабной рекламой.
- SMS/MFA/refresh-ответы исключены из кэша идемпотентности. Использованный OTP или refresh-токен нельзя повторно обменять на токены через повтор запроса. Обновление сессии атомарно в БД. Заблокированный пользователь не получает сессию.
- Включённую 2FA нельзя сбросить повторным вызовом setup. Изменения защищены лимитом попыток. Админка объединяет параллельные обновления сессии в одном процессе; перед горизонтальным масштабированием Next.js потребуется общий механизм координации.
- Очередь обрабатывается в порядке поступления, повторные попытки уступают место ожидающим задачам. Повреждённое сообщение изолируется; после трёх неудачных попыток задача остаётся в очереди ошибок для разбора. Отмена задачи при остановке worker оставляет её для восстановления. Гарантия обработки — как минимум один раз, а не ровно один раз.
- Раздел «Интеграции» получает `/v1/admin/operations`: состояние worker, количество ожидающих, выполняемых и неудачных задач, лимиты SMS. Доступ есть только у администраторов и модераторов; содержимое заданий и пользовательские доказательства не выдаются.

## Поведение релиза

- Публичные HTML-каталоги, фильтры, карточки и sitemap доступны без входа. Черновики, непроверенные и закрытые вещи исключены.
- Владелец дорабатывает черновик и фотографии. Изменение опубликованной карточки требует повторной модерации; пропажу можно описать без фото.
- Держатель и уполномоченные сотрудники рассматривают ответы, доказательства и скрытые признаки. Роль viewer не допускается к доказательствам, решениям и чату заявления.
- Чат принимает JSON-события WebSocket; при обрыве продолжает получать сообщения через HTTP. QR-передача завершается двумя подтверждениями, повторный запрос не создаёт второй возврат.
- Администратор видит фотографии, редактирует карточки и отвечает пользователю в поддержке. CSV организации создаёт черновики; невалидный CSV отклоняется до записи.
- Публичные фотографии декодируются, проверяются и сохраняются без EXIF/GPS. Демо-наполнение отключено по умолчанию и всегда отключено в production. Ранее созданные демо-записи автоматически не удаляются.
- Маркетинговые счётчики отражают события за 30 дней с момента установки, не уникальных пользователей. Они включают повторные просмотры и роботов. Срок хранения — 90 дней; cookies, IP и поисковые запросы не сохраняются.

## Настройки VPS

В корневом `.env` вместе с существующими секретами:

```dotenv
BN_ENVIRONMENT=production
PUBLIC_BASE_URL=https://edinburo.ru
ADMIN_BASE_URL=https://admin.edinburo.ru
ADMIN_COOKIE_SECURE=true
S3_PUBLIC_URL=https://edinburo.ru
BN_CORS_ORIGINS=["https://edinburo.ru","https://admin.edinburo.ru"]
BN_SEED_DEMO_DATA=false
MINIO_BIND=127.0.0.1
```

Шлюз проксирует приватный bucket `/bureau-media/`, сохраняя путь и Host подписи. HTTPS обслуживается внешним прокси. DNS `admin.edinburo.ru` и TLS нужно проверить отдельно: на 4 сентября DNS возвращал NXDOMAIN. Не выводите значения секретов в журналы; используйте `docker compose config --quiet`.

SSH-ключ workflow вызывает ограниченную принудительную серверную команду. Её исходника нет в репозитории; 4 сентября Git fetch прошёл, но сборка Flutter на VPS исчерпала 45-минутный лимит. Исходник forced command пока недоступен; по логу она может вызывать Compose напрямую. Ограничение SSH сохраняется. При ошибке команда должна возвращать ненулевой exit code. Вызов `./install.sh` допустим только после успешного получения нужного commit. Checkout сам по себе не доказывает запуск релиза.

## Установка и откат

`./install.sh` переводит известные старые HTTP-адреса localhost/этого VPS на HTTPS-домены проекта и включает Secure для cookie админки. Пользовательские HTTPS-endpoint и секреты сохраняются. Затем он подготавливает образы до замены контейнеров, запускает их, проверяет точный SHA API/worker и маршруты. В production Flutter не компилируется: Dockerfile получает готовые файлы из GitHub Release `runtime-<SHA>`, проверяет SHA-256 и встроенный SHA. CI публикует их только после тестов, Docker smoke-test, проверки резервной копии и проверки самого пути доставки. Отсутствующий или повреждённый артефакт останавливает сборку. В development `install.sh` использует `compose.source.yml` для сборки из исходников. Образы помечаются SHA; успешный SHA записывается в `.releases/current`. Workflow дополнительно сверяет публичный SHA с commit успешного CI. Backend-образ содержит SHA из Git HEAD, поэтому версия корректна и при старом прямом вызове Compose без `BN_RELEASE_SHA`. В корневой Docker-контекст допускаются только исходники и Git HEAD/refs; `.env`, Git config и objects туда не попадают. При старом прямом вызове Compose backend также переводит известный публичный адрес этого VPS на canonical HTTPS, включает production-проверку секретов и исправляет известный старый адрес MinIO. Пользовательские endpoints и ключи сохраняются. Cookie админки получают Secure на HTTPS-запросах независимо от прежнего флага `.env`. Git checkout обязателен для Docker-сборки. Установка из ZIP исходников не поддерживается.

Установка, откат и создание копии используют общую блокировку `flock`: запуск одновременно с другой операцией завершается понятной ошибкой. На сервере нужен пакет `util-linux` (обычно установлен в Linux).

Прямой серверный вызов Compose не записывает нормализованные настройки в `.env` и не выполняет блокировку и запись истории релизов из `install.sh`: для этих функций forced command должна после успешного checkout вызывать `exec ./install.sh`. До проверки этой серверной настройки нельзя считать откат и нормализацию production-настроек принятыми.

`./scripts/rollback.sh <SHA>` использует сохранённые Compose/Nginx и ранее собранные образы. Downgrade схемы базы не выполняется. Откат к версиям, существовавшим до введения тегов и сохранения конфигураций, этим скриптом не поддерживается. Предыдущие образы сохраняйте до окончания приёмки.

## Копии и восстановление

На VPS нужен `age`. Создайте закрытый ключ вне репозитория с правами 600, например `age-keygen -o /etc/buro/backup.agekey`, и сохраните отдельную защищённую копию. Публичный получатель выводится командой `age-keygen -y /etc/buro/backup.agekey`.

В окно обслуживания:

```sh
BACKUP_RECIPIENT=age1... ./scripts/backup.sh
BACKUP_IDENTITY=/etc/buro/backup.agekey ./scripts/restore-check.sh backups/<архив>.tar.age
```

Копирование временно ставит API, worker и MinIO на паузу для согласованности БД и файлов; в этот период сервис недоступен. Архив включает БД, media, секрет OpenAI и конфигурацию. Храните зашифрованную копию вне VPS. `restore-check.sh` реально восстанавливает БД в отдельную временную базу и проверяет чтение архивов media/секретов. Полное восстановление запасного сервера необходимо проверить отдельно. Расписание копирования без выбранного окна обслуживания автоматически не устанавливается.

CI проверяет создание зашифрованной копии тестового Docker-стека, расшифровку, восстановление отдельной базы и работоспособность приложения после снятия паузы. Это не заменяет проверку резервирования production-данных и хранения копии вне VPS.

## Финальная ручная приёмка

1. Два пользователя проходят реальный SMS-вход, публикацию с фото, модерацию, заявку с доказательством, решение, чат, обмен согласием и QR-передачу с двумя подтверждениями.
2. Проверяются смартфон, компьютер, смена сети в чате и запрет доступа к чужим черновикам/доказательствам.
3. Выполняется реальный запрос OpenAI с фотографией. `configured` в health сообщает только о конфигурации, не об успешном запросе или балансе.
4. На VPS проверяются SHA, DNS/TLS обоих доменов, резервная копия, восстановление и откат.
5. Владелец подтверждает реквизиты оператора, действующий адрес поддержки и юридические документы. CI и доступность сайта не подтверждают юридическую готовность.

До этой приёмки релиз не объявляется готовым к массовому запуску.
